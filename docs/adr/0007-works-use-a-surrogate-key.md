# 作品用代理键，身份是它下面的一张多键表

实测一对已标注的同一作品（`aiqiyi.ai/voddetail/237486.html` 与 `tvmao.com/kanju/YmFfZmsg`，都是《无可替代》）后确认：不存在一个跨站通用的单一身份字段。番号站有内容编号；剧集站的 URL 是站点内部 ID，标题里没有编号；元数据站只有文本。因此 `works` 不能用 `code` 作主键，改用代理键，身份键是它下面的一张多值表，任何一路命中即归并。

## Considered Options

- **`code` 单一主键**（ADR-0004 原方案）：对番号站成立，对实测的剧集站与元数据站不成立。
- **挑一个"最好"的字段当键**：跨站不可行。封面哈希在同一个采集生态内的 MacCMS 站之间可能共享，但跨到元数据站必然不共享——实测两个方向的图床完全不相交。
- **代理键 + 多值身份键**（选中）。

## Consequences

- `works(id PRIMARY KEY)` 用代理键；`work_keys(work_id, kind, value)`，`UNIQUE(kind, value)`。`kind` 至少包括：内容编号、封面哈希、标题归一化、简介指纹。
- 每路信号的可信度不同，必须在**代码里分级**，而不是在判定器里混着算：编号与封面哈希是高精度低召回；文本指纹是低精度高召回。这正好对上 ADR-0002 里"误合比误拆更贵"的三档划分。
- **简介指纹不能靠精确相等。** 实测：一方的 `<meta name="description">` 被截断到 114 字、以 `...` 结尾，另一方是完整的 150 字，相似度 **0.8216**，共同前缀 66 字。指纹必须取**归一化前缀**。
- 这张表的形状与 `agent_memories(type, key, value, weight)` 一致，可以直接借用同一套权重衰减。
- 归一化（标题剥后缀、简介取前缀、封面只留哈希）必须由程序统一实现，不能让适配器各写一遍。
