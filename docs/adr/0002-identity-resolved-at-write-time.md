# 身份判定在写入时做出并落库，不确定的交给用户裁决

跨站兴趣融合要求「作品」是一个独立于站点的实体，而这些站点不提供任何内容编号，标题里全是噪声（"中文字幕 / 高清 / 无删减 / 1080p"）。因此身份判定的结果是三档而不是两档：同一部作品（合并）、不同作品（不合并）、以及两者都不安全的中间档（交给用户确认）。判定在扩展上报访问的写入路径上做出，结论写入数据库；不在每次读取时重新推断。

## Considered Options

- **读取时交给 LLM 容错**：LLM 看到重复输入不会出错，但那只是一次性的临时判断，不留痕。判定结果无法留存，用户的纠正无处可放，兴趣画像会在两次运行之间漂移——而 `agent_memories` 的权重是持久化的指数平滑（`newWeight = existing*0.7 + weight*0.3`），漂移会被固化且没有历史可回滚。上下文窗口还会成为历史容量的上限。
- **纯算法归一**：站点无限多且不配合，这是 O(站点数) 的适配器维护成本，永远还不完。
- **写入时判定并落库**（选中）：一次判定只做一次，可复现，可被用户纠正，成本从「每次读取 × 全量历史」降到「每次歧义 × 一次」。

需要判定，是因为站点不提供结构化字段；但站点页面上其实**写着**内容编号，只是散落在 URL 或标题的噪声里。因此主路径是**解析**而不是判定：适配器从页面抽出内容编号，编号就是作品的身份。只有当适配器抽不出编号、或两条记录的编号对不上却仍然存疑时，才需要模糊判定。**不要为已经有编号的情况建一套判定器。**

## Consequences

- 判定要看到标题等原始字段，这意味着数据会离开本机，与 AGENTS.md 里的 privacy-first 定位及默认的本地 Ollama provider 冲突。送出前必须由站点适配器先抽出最小字段集。
- 中间档写进已有的 `agent_pending_actions` 队列，复用 approve / dismiss 通道；用户的裁决由此成为后续判定的标注数据。
- 判定错误的代价不对称：误合（把两部不同作品焊成一部）比误拆更贵——误合会通过上面的指数平滑永久固化，而且用户很难发现；误拆只是信号变弱，排序仍然正确。
- 「作品」成为一等实体，`records` 降为访问事件，`watchlist` 降为站点适配器。
