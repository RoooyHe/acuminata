# 适配器按平台组织，并内置 MacCMS 适配器

两个真实站点被拉下来对比后证实是同一平台：

```
mgtvtv.com   var maccms={"path":"","mid":"1","aid":"11","url":"www.mgtvtv.com",...}
aiqiyi.ai    var maccms={"path":"","mid":"1","aid":"11","url":"aiqiyi.ai",...}
```

而它们的**路由、主题、class 名、分页形状、懒加载属性全部不同**（对比表见 `docs/adapters/template.md`）。

这反向证明了本决定：如果按站点写适配器，上面每一栏都要逐站重写，而且主题一改就废；按平台写适配器，知识是共享的，只是不通过 class 共享。决定：适配器按**平台**组织，用页面签名检测而不是用域名或 URL 形状绑定，并内置一个 MacCMS 适配器；用户编写的适配器只覆盖非 MacCMS 的站点。

**这条修正 ADR-0003 的理由。** ADR-0003 否掉“内置适配器”的依据是“O(站点数) 的维护成本，个人项目追不上”——前提错了，所以结论要调整（决定本身保留）。

## Consequences

- 模板的 `domain` / `mirrors` 不再是主轴。改为 `detect`（页面签名）＋ 可选的 `domains`。
- **URL 形状不能用来检测平台**：同一平台的两个站路由完全不同。只有签名能。
- 平台级适配器需要有序备选的选择器与属性（`from: [...]` 的同一个概念），详见模板文档。
- 冷启动大幅改善：装上就能在多数站点工作，不需要用户先写规则。这削弱了 ADR-0003 里“目标用户是愿意写规则的进阶用户”这个限定的强度。
- 平台签名可能被站点改掉，所以内置适配器仍然需要“失效可见”的告警，不能静默。
- 内置与用户编写的适配器必须是**同一种格式、同一条管道**，不得有特权路径。“要不要内置更多平台”因此是一个可以随时改的主意，而不是一个架构赌注。
